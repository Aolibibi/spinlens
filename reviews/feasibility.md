## 2. BLOCKER

### B1 · 游标失效会静默重放第一页，而 §9.1 的终止条件防不住 → 死循环

**【实测】** 把 `pagination_str` 里的 offset 换成任何服务端不认的东西（`not-a-valid-cursor`、`AAAA`、`!!!!`、甚至一个字段合法的伪造 protobuf），接口的反应是：

```
code = 0
replies = 30 条，rpid 与第一页完全相同
cursor.pagination_reply.next_offset = 一个正常的、非空的、与上一页不同的新游标
```

**为什么是问题**：§9.1 第 6 行白纸黑字写着"**终止条件必须是 `is_end` 或 `next_offset` 为空**"。而在这个失败模式下，这两个条件**永远不成立**——`is_end` 一直是 false，`next_offset` 一直是一个合法字符串。于是循环会永远重放第一页：1802 条的视频变成无限循环，内存线性增长，最终 OOM；而 `errorCount` 始终是 0，摘要会打印"`0 错误`"。触发条件一点都不苛刻：游标过期、字符串被 JSON 双重转义、base64 被 urlencode 破坏、参数集合变化、复制粘贴截断——**任何一次都能触发**。

**特别注意**：拿"新 offset 是否与上次相同"来判死**没用**——实测垃圾游标换来的是一个**不同**的 next_offset。

**怎么改（§9.1 第 6 行整条替换）**：

> 6. 翻页终止条件（三条并列，任一成立即停）：
>    a) `cursor.is_end === true` 或 `next_offset` 为空；
>    b) **本页 rpid 有序集合与上一页完全相同**（游标失效特征，实测服务端会静默重放第一页）→ 立即中止，记 `errorCount + 1`，摘要标注 `cursorStalled: true`；
>    c) 全局重复率 > 50%（兜底，防"重放第 N 页"这种非首页重放）。
>    **禁止**用"新 offset 是否变化"判定，实测无效。

### B2 · 风控降级只给 3 条时，与"真的只有 3 条"无法区分 → 报告会撒谎

**【实测】** `/x/v2/reply/wbi/main` 带上 `buvid3+buvid4` 半套 cookie → `code=0`、**只返回 3 条**；不带 cookie → 30 条。旧端点不带 cookie → `code -352`。也就是说：**降级不报错，它只是安静地少给你东西。**

**为什么是问题**：§13 的 R3 说"用户误读抓漏了"是**高概率**风险，缓解方案是"摘要同时显示主评论数与 all_count"。这个缓解**对风控降级完全无效**——降级时摘要会打印：

```
抓取  主评论 3 条｜总评论 6826 条(含楼中楼 5015)｜0.3s｜0 错误
识别  命中 0 条 (0.0%)
```

两个数字自相矛盾，却自称成功、退出码 0。这正是"数字对不上还说自己没错"的最坏版本，对一个以**可核对**为公信力的工具是致命的。触发路径很现实：用户看 §3-S6 手动加了 `--cookie`、或实现里用了会自动回传 Set-Cookie 的 HTTP 客户端、或 B站哪天开始给游客下发 cookie。

**怎么改（§9.1 新增"降级自检"，§11.1 摘要加字段）**：

> §9.1 第 7.5 条（新增）**降级自检**：首页返回条数 `n === 3` 且 `cursor.all_count > 3` 时，判定为风控降级（实测特征），**默认拒绝出报告**，打印：
> 「接口只返回了 3 条（疑似风控降级）。请去掉 `--cookie` 后重试；若你确实需要登录态数据，请自行承担风险。」
> 退出码 2。用户显式加 `--allow-partial` 才继续，且此时摘要首行必须打 `⚠ 数据不完整`。
>
> §11.1 摘要的"抓取"行改成：`主评论 N 条｜总评论 all_count 条(含楼中楼 M)｜已抓 P/Q 页｜耗时｜K 错误`；只要不是完整抓完，行尾追加 `⚠ incomplete`。

## 3. MAJOR

### M1 · "单文件 ≤60KB"与"规则外置"、"A 档 Node 单文件"三方矛盾

§12 写"体积：单入口文件 ≤ 60KB（**不含规则 JSON**）"，§6 写规则是"**外置 JSON**"，附录 A 又写"A 档（**Node 单文件**）"。三者不能同时成立。

**先回答"60KB 是否合理"**：**体量上完全可行**——WBI 签名 ~60 行、翻页与重试 ~120 行、检测 ~80 行、报表 ~120 行、CLI ~80 行，加中文注释大约 30–45KB；默认规则内嵌再 +8–12KB。所以 60KB 不是苛刻。**问题在于这个指标没有意义且自相矛盾**：它逼着规则外置（于是不再是单文件），又和同一张表里的"关键路径有中文注释"打架（会诱导 minify）。

**怎么改**：
- §12 体积行改成：`**单入口文件包含内置默认规则，≤ 80KB**；`rules/*.json` 仅作示例与导出用途`；
- §6 补一句：`不提供 --rules 时使用**内嵌**的默认规则；`--dump-rules > my-rules.json` 可导出后再改`。这样"复制一个文件就能跑"成立，S4 的扩展性也不丢。

### M2 · 没有"抓不到时的兜底路径"——这是我最建议花 30 行代码换的东西

§13 的 R1 承认"B站改签名 = 致命"，缓解只有"明确报错 + 升级指引"。但工具此时**什么都产不出来**。对一个定位"抛砖引玉"的视频来说，那一刻观众的结论不是"接口变了"，是"**这东西是假的**"。而且 R2 的 `-352` 我这次实测**真的撞到了**（旧端点），这不是小概率。

**怎么改**：
- §10 新增 `--from-json <file>`：读一份已有评论 JSON，跳过 Fetcher 直接进检测/报表；
- §10 新增 `--demo`：随仓库分发一份样本评论（就用本期视频的 1802 条），全链路离线可跑、结果确定、适合录视频；
- §13 R1 的缓解补一句："接口失效时，`--from-json`/`--demo` 保证检测与报表链路仍可演示与验证"。

顺带解决 M1（样本数据外置）、M15（内存）、以及 §12"Fetcher 可注入"的落点。

### M3 · §9.1 完全没写 HTTP 头，而带错 Referer 是 HTTP 403 硬拒

**【实测】** 不带任何头 → `code 0`；只带 UA → OK；只带 Referer → OK；**Referer 填 `https://example.com/` → HTTP 403 + 空 body**（不是 JSON，没有 code）。

**为什么是问题**：① 规格不写头，实现的人会凭"常识"随手加一个 Referer（甚至加视频页 URL、b23 链接），一旦不对就是 403；② 403 的 body 是空的，`await res.json()` 会抛 `SyntaxError: Unexpected end of JSON input`——用户看到"JSON 解析失败"，真实原因是风控拒了。对一个要给陌生人跑的工具，这是最典型的"看不懂的报错"。

**怎么改（§9.1 第 4 条后插入）**：
> 4.5 请求头：只带 `User-Agent`（可选）；**不要设置 `Referer`**（实测不带也能通过；若设置则必须精确为 `https://www.bilibili.com/`，写错会得到 HTTP 403）。**所有响应必须先判 `res.ok` 与 `content-type`，非 JSON 一律按 HTTP 状态码报错，禁止直接 `.json()`。**

### M5 · Node 版本底线是假的

**【实测】** 本机 `node -v` = **v24.13.0**。SPEC §12 承诺 ≥18.17，但：① 所有实测都在 24 上跑，**从没在 18 上验证过**；② Node 18 已于 **2025-04-30 EOL**；③ 18.x 的全局 `fetch` 仍标记为 experimental，首次调用会向 stderr 打印 ExperimentalWarning（会污染终端摘要这个"产品本体"）【推断，未在 18 上实测】。

**为什么是问题**：这是标准的"我这能跑"。观众里装了 Node 16/18 的人不会看到"版本太低"，只会看到 `fetch is not a function`。

**怎么改**：§12 改成 `**Node ≥ 20.19 或 ≥ 22 LTS（作者实测环境：Node 24.13 / Windows）**`；README 第一步写"运行 `node -v`，低于 20 请先升级"；程序启动做一次版本守卫，输中文提示而不是崩溃。

### M6 · Windows 下 `>` 重定向会写出 UTF-16LE，废掉 §11.2 的 BOM 承诺

**【实测】** 本机 PowerShell **5.1**（我们此刻就在用它）执行 `node -e "console.log('123...')" > x.txt`，产物开头是 **`FF FE`（UTF-16LE）**，不是 UTF-8。PowerShell 7 的 `Out-File -Encoding utf8` 才是 `EF BB BF`。

**为什么是问题**：观众照 README 写 `node huashu.js BVxxx > out.csv`，拿到的是 UTF-16LE——绕过了 `--out` 里的 BOM 逻辑，Excel 可能能开、但任何脚本都读不了；而且文件名里还少了他以为会有的时间戳。

**怎么改**：§11.2 或 README 明写："**不要用 `>` 重定向输出 CSV，请用 `--out 文件名.csv`**（`--out -` 只用于管道）"。§12 加一行平台注意事项。

### M7 · 网络错误必须展开 `err.cause`；Node 不读代理环境变量

**【实测】** ① 未知域名 → `TypeError: fetch failed`，真正原因只在 `err.cause.code`（`ENOTFOUND`）；② 把 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 指向一个**关闭的端口** `http://127.0.0.1:1`，`fetch` **照常成功** → 全局 fetch **完全忽略**代理环境变量。

**为什么是问题**：① 公司/校园网用户必挂，看到的只有"fetch failed"四个字，网上搜不到答案；② 想挂代理的用户以为设了环境变量就行，其实无效；③ §12 的"零第三方依赖"意味着**加不了代理支持**（undici 的 ProxyAgent 是依赖），所以只能把话说清楚——那就更要说清楚。

**怎么改**：§12 网络鲁棒性补两句：
> - 所有网络错误必须输出 `err.cause.code`（`ENOTFOUND` / `ECONNREFUSED` / `ETIMEDOUT` / `ECONNRESET`）并给出中文解释，禁止只打印 `fetch failed`；
> - 本工具**直连** `api.bilibili.com`，**不读取系统代理，也不读取 HTTP_PROXY/HTTPS_PROXY**（实测）。需要代理的用户请使用全局/TUN 模式。README 必须写明这一点。

### M8 · CSV 只给 `msg` 转义是错的；且缺公式注入防护

§11.2 写"`msg` 做 CSV 转义（双引号翻倍）"。但：

- `evidence` 的格式 `T1:pattern(两边.{0,8}都.{0,8}有问题)@12-24` —— **`{0,8}` 里那个逗号是必然存在的**，所以 evidence 列**一定**会撑断行；
- `user`（B站昵称）可以含逗号、引号、emoji；
- **【实测】25/1802（1.4%）的评论正文以 `=`、`+`、`-`、`@` 开头** → 在 Excel / Google Sheets 里会被当**公式**执行（经典 CSV 注入）。这不是理论风险。

**怎么改（§11.2 两条替换/新增）**：
> - **所有字段**统一走同一个转义函数（含 `"` 翻倍、需要时整体加引号），不是只有 `msg`；
> - 字段以 `=`、`+`、`-`、`@`、`\t`、`\r` 开头时，前置一个单引号 `'` 中和公式（实测 1.4% 的评论命中这条）。

### M9 · 证据的字符区间与原文对不上（换行 + emoji 代理对）

§5 说 `msg` 是"已做换行归一"，§7.3 又要求输出"原文片段与字符区间"。**【实测】164/1802（9.1%）的评论正文里真的有换行符**；**【实测】114/1802（6.3%）含 emoji（UTF-16 代理对）**。

**为什么是问题**：① 如果归一化不是**等长**替换（比如折叠连续空白、trim），全部区间整体偏移，用户拿着 `@12-24` 回原文找，找不到 → §7.3 的"公信力底线"当场破功；② `String.prototype.slice(a,b)` 按 UTF-16 code unit 计，用它去切命中片段**有机会切出半个代理对**，输出成 `�`。

**怎么改**：
> - §5：换行归一 = 把 `\r\n` / `\n` 各替换为**同长度**的空格；**不 trim、不折叠连续空白**（否则区间失真）；
> - §7.3：证据片段**直接取 `match[0]`**，不要用区间去 `slice` 原文；若必须输出区间，注明基准是"归一后的字符串"。

### M10 · `--max-comments` 默认"不限"是错的（10 万条评论区实测外推）

**【实测】** 1802 条评论的接口原始 JSON = **12.33MB**，**平均 7176 字节/条**（B站的 reply 对象里塞了 `member/nameplate/vip/reply_control/track_info/assist/action` 等一大堆用不上的东西）。

- 如果实现是"把每页的 `data.replies` 原样 push 进数组"（§4.1 的 `fetchAll → Comment[]` 非常容易被这样偷懒），**10 万条 ≈ 684MB 堆占用** → 8GB 笔记本上 GC 抖动甚至 OOM；
- 如果按 §5 的 Comment 模型**每页立即映射**（只留 8 个字段），单条约 300B，**10 万条 ≈ 30MB**，毫无压力。

时长：10 万 / 30 ≈ **3334 页**；实测 7.15 页/秒 → 约 **8 分钟**；再加默认 120ms 节流 ≈ **14 分钟**。

**怎么改**：
- §4.1 加一句：`每页响应返回后**立即**映射为 Comment 并丢弃原始 reply 对象，禁止累积原始 JSON`；
- §10 `--max-comments` 默认值从"不限"改成 **2000**，并打印一行"已达上限 2000 条，`--max-comments 0` 可解除"；理由：对"陌生人试一下"来说，14 分钟等于劝退，而视频演示 2000 条足够。

### M11 · 风险表漏了合规边界与真人信息

我核对了 §13 的 R1–R6：覆盖了技术、误报、工具化。**没有一条覆盖"抓取行为本身的平台规则/法律边界"，也没有一条覆盖"CSV 里默认带真人昵称"**。而 §11.2 的 CSV 默认包含 `user`（昵称）+ `rpid` + `evidence`，配合 §11.2 的原文列，导出的东西天然就是一张"**谁说了什么**"的名单；§3-S3 还支持一次跑多个 BV 号。

**怎么改（§13 补两行 + §11.3 加一句）**：
> | R7 | CSV 被当挂人名单转发 / 被用于批量采集 | 中 | 道德/合规 | 提供 `--anon`（昵称替换为短哈希）；README 写死"仅供个人研究，**请勿把 CSV 直接转发到评论区**，禁止批量采集与商业用途"；**不提供"一次抓 N 个视频"的循环参数** |
> | R8 | 平台规则边界 | 低 | 工具下架 | README 声明"仅读取公开数据、仅个人研究、不提供托管服务、不代抓" |
>
> §11.3 补：免责声明**必须同时写进 CSV**（文件末尾追加一行 `# 本结果由当前规则匹配得出，不是事实判定`），因为 CVS 会被单独转发，而摘要不会。

### M12 · 不支持 b23.tv 短链 —— 观众最可能当场放弃的一步

§9.1 第 1 步只写"完整 URL / BV 号 / av 号"。但 B站 App 的分享按钮产出的是 `【视频标题】 https://b23.tv/XXXXXX` 这种**带标题的短链文本**；网页分享产出的是带 `?share_source=copy_web&vd_source=...` 的完整 URL。（**诚实标注**：本机 `curl.exe` 在沙箱里不通，b23.tv 的跳转我**这次没能实测**，属于通识推断。）

**为什么是问题**：录视频时你自己就是"从 App 复制 → 粘贴到命令行"，如果解析器只认裸 BV 号，**第一个动作就报错**。观众自己试第一次也一定踩这里。

**怎么改（§9.1 第 1 步扩成"宽容解析"）**：
> 输入解析顺序：① 从整行文本里正则抽 `BV[0-9A-Za-z]{10}` → 直接用；② 抽不到就抽 `av\d+`；③ 抽不到就抽 `https?://\S+`，若是 `b23.tv` / `bili2233.cn` 则**跟随一次跳转**后再抽 BV/av；④ 忽略标题、空格、emoji、`?` 之后的全部参数。都不行才报错。
> README 示例给一条带引号的粘贴用法：`node huashu.js "【标题】 https://b23.tv/xxxxx"`。

### M13 · M1 的"完整度 ≥98%"没给公式

M1 写"主评论完整度 ≥ 98%（用 §2-B3 的方法核算）"——"§2-B3 的方法"是一段散文，不是可执行的判定。**怎么改（§14 M1 验收列直接写成公式+命令）**：
> `完整度 = (抓到的主评论数 + Σ抓到的主评论的 rcount) / cursor.all_count`，且必须 **`is_end === true`**；要求 ≥ 0.98。验收命令与输出贴进 README。

### M14 · M2 的"准确率 ≥80%"不可度量（用户点名问的一条）

现在这句话没有定义、没有数据集、没有可跑的命令，三个人会用三种方法算出三个数。**怎么改（§14 M2 验收列整条替换）**：
> 1. 从被测视频**随机抽 200 条主评论**（固定随机种子，抽样结果落盘到 `eval/sample-<bvid>.csv`，保证可复现）；
> 2. 人工标注每条"是/不是话术"，落盘 `eval/golden-<bvid>.csv`；
> 3. `node eval.js eval/golden-<bvid>.csv out.csv` 输出混淆矩阵与 `precision / recall`；
> 4. **验收 = precision ≥ 0.80**；recall 只记录、不设门槛（"筛子"定位下，**误报比漏报更伤公信力**）；
> 5. "误报能被 exclude 或调阈值压住"改成可验收的形态：**对标注出的 5 条典型误报，README FAQ 里各给一句 `--min-score` 或 `exclude` 的压法，并能用命令复现**。

注意：没有负样本集时，precision 可以靠调阈值"刷"出来，所以抽样的 200 条里必须包含大量"明显不是话术"的普通评论。

### M15 · nav / WBI 密钥取不到时的路径没写

§9.1 第 3 步直接 `nav → wbi_img → imgKey/subKey`。若 nav 异常、或 `wbi_img` 为空（风控/接口变更），`img_key` 就是 `undefined`，之后**每一个**请求都返回 `-403 访问权限不足`，用户看到的是"权限不足"，会以为要登录。

**怎么改（§9.1 第 3 步补半句）**：
> 校验 `data.wbi_img.img_url/sub_url` 存在且非空；缺失则报「无法获取签名密钥（WBI），接口可能已变更或被风控拦截」，退出码 2，**不要继续发起后续请求**。

### M16 · `--ai` 的"静默降级"与报告可信度冲突（顺带：隐私）

§8.2 说解析失败/超时/无网 → **静默**降级。用户会以为那 41 条都经过模型复核了。

**怎么改**：§8.2 把"静默"改成"不中断流程，但必须计数并显示"；§11.1 摘要加一行 `AI  已复核 37/41 条（4 条降级为规则原判）`。另外补一句隐私提示：`AI 精排会把命中评论的原文（含昵称）发送到用户指定的端点，启用前必须提示`。

## 5. 规格写对了、我已核对无误的部分（免得以为我漏看）

1. **`wts` 时间戳/时钟偏移不是风险** —— 实测 `now±30s / ±1h / ±24h` **全部 `code=0`**。"跨秒失效""本机时钟不准"这两个担心可以划掉，**签名不需要校时**。
2. **签名错误的表现是确定的** —— w_rid 错/缺 → `code -403 访问权限不足`，不是静默失败。所以 R1 的"给出明确报错"是可实现的。
3. **游标与 session 无关、可跨进程复用** —— 上一个 Node 进程拿到的 next_offset，在**全新进程**里直接使用，返回的正是同一页（首条 rpid 一致）。所以"断点续传"在技术上成立。
4. **`ps` 上限确实是 30** —— §2-B5 正确。
5. **翻页不重复** —— 61 页 1802 条，rpid **零重复**。
6. **`mode=2` 确实是"最新优先"**（新版在前）。
7. **终止判定本身可靠** —— 第 61 页 `is_end=true`，正好 1802 条。
8. **"默认不带 cookie"是硬性正确的** —— 实测 WBI 端点带半套 cookie → 3 条，不带 → 30 条。§2-B7 完全成立。**建议再加一句"连一个字节都不要带"**，并禁止使用会自动回传 Set-Cookie 的 HTTP 客户端。
9. **零依赖可行** —— 我全部探针只用 `node:crypto` + 全局 `fetch`。
10. **§8.1 用 `#` 作分隔符没问题** —— 我担心过 PowerShell 把 `#` 当注释，**实测不会**，参数完整传给了进程。
11. **§11.2 的"换行归一为空格"是必须的** —— 实测 164/1802 的评论真的含换行。（但见 M9：必须**等长**替换。）
12. **§4.3 的 seam 判断是对的** —— "平台采集"是真 seam（小红书确实要签名+登录态，与 B站免登录形成对照）。

**关于"断点续传是否必要"的正面回答**：**不做续传，要做"失败也出报告"**。续传技术上可行（见第 3 条），但它会引入状态文件（写哪、怎么命名、版本怎么对、二次运行怎么合并）——典型的过度设计。观众真正的痛点不是"想接着上次跑"，而是"跑了 40 秒挂了，什么都没有"。所以：**抓取失败时仍然输出已抓到的部分 + 摘要明确标注 `incomplete`**，成本十几行。真需要续传时，M2 的 `--from-json` 就是它的雏形。

| **Shell 重定向** | PS 5.1 的 `>` = **UTF-16LE**（实测 FF FE） | README 必须禁用 `>`（M6） |
| **代理** | 全局 fetch **忽略** HTTP_PROXY/HTTPS_PROXY/ALL_PROXY（实测） | 公司/校园网用户会挂，且只看到 "fetch failed"（M7） |
| **地域 / 海外 IP** | **未验证**：本机 `curl.exe` 在沙箱里不通，出口 IP 服务也拉不到 | **我没有数据**。建议发视频前用一台海外 VPS 跑同一段探针；若海外不行，README 写一句"请在境内网络使用"能省掉大量 issue |
| **磁盘/写权限** | 默认写 CWD | 只读目录会失败，需给提示 |
| **时间同步** | 实测 wts ±24h 都通过 | **不需要联网校时**，这条可以从风险里划掉 |

另外两条反直觉但已被实测确认的：**"零 Cookie"必须做到字节级**；**"日志/控制台编码"是作者已被掩盖的变量**。

### 6.2 §9.1 的抓取流程有哪些工程坑没写？

按你点名的五个子问题逐个答：

1. **`wts` 跨秒/时钟偏移** → **不是风险**（实测 ±24h 全通过）。可以放心写"用当前秒"。
2. **游标 offset 是否与 session 绑定/隔天能否续翻** → offset 是**不透明 protobuf**（`08011a0032030 8XX16`：字段1=type、字段3=空、字段6一段 varint），**不是页码、不是行号**，所以**绝不能自己构造**（我伪造过，服务端直接忽略并重放第一页）。跨进程复用**实测可行**。隔天是否过期我没测（需要等一天），建议实现里**不要依赖长期有效的游标**。
3. **翻页中途失败如何续传** → **不要做续传，要做"失败也出报告"**（见 §5 末尾）。
4. **10 万条会怎样** → 页数 ≈ 3334、约 8 分钟（带默认节流 ≈ 14 分钟）；**内存风险全在"是否每页立即映射"**：原样累积 ≈ 684MB，按 Comment 映射 ≈ 30MB（M10）。
5. **并发/批量风控** → 25 次零延迟串行 + 8 并发全部 `code 0`，**但我在旧端点实测撞到 `-352`**，说明这个 IP 已被标记。结论：**保持串行 + 保留节流，S3 批量不要并行**。
6. **（你没点名但更致命）垃圾游标静默重放第一页** → **B1**，这是 §9.1 最大的工程坑。
7. **更多没写的**：HTTP 头（M3）、错误码表（M4）、nav/WBI 密钥为空的处理（M15）、风控降级自检（B2）、输入宽容解析（M12）。

### 6.3 §12 是否自相矛盾/不现实？"单文件 ≤60KB"合理吗？

**存在两处矛盾**：
- **"单文件 ≤60KB（不含规则 JSON）" × "规则外置 JSON" × "A 档 Node 单文件"** —— 三者不能同时成立，分发物其实是 1 个 JS + N 个 JSON（M1）；
- **"体积 ≤60KB" × "关键路径有中文注释"** —— 不严格冲突，但 60KB 这个预算会诱导实现者去做 minify，直接伤害同表要求的可读性。

**60KB 本身合理**：按模块估算 30–45KB + 内嵌规则 8–12KB，落在这个量级。**但这个指标没有工程价值**，建议换成"单入口文件包含内置默认规则，可直接 `node` 运行，无构建步骤"。

**另外 §12 缺一条**：模块系统（CJS vs ESM）没有定，而它同时被"单文件"和"可注入/可单测"两条要求夹住（见 NIT）。

### 6.4 §11.2 的 CSV 设计

- **UTF-8 with BOM 是否真能解决 Excel 问题？** —— **能，但只在你用 `--out` 的时候**。一旦观众用 `>` 重定向（Windows PowerShell 5.1），写出的是 UTF-16LE，BOM 逻辑被绕过（M6）。所以 BOM 是对的，**但要配一条"不要用重定向"的说明**。
- **字段含逗号/引号/换行** —— 换行确实存在（164/1802，SPEC 已正确处理）；逗号/引号量很少但**必然有**；**真正被漏掉的是 `evidence`（`{0,8}` 里的逗号是必然的）和 `user`**；并且实测 **25/1802 的行以 `=+\-@` 开头 = CSV 公式注入**（M8）。
- **超长评论截断策略缺失** —— **实测最长 963 字符、59 条 >200、0 条 >1000**。结论：**CSV 里不该截断**（963 字符完全可以接受），需要限长的是 **AI 层**送出去的候选评论（建议截到前 300 字符）。把这两句写进规格，"超长评论"这件事就有答案了。
- **emoji** —— 114/1802 含代理对；BOM 的 UTF-8 能装下，但**终端摘要里的对齐**会因 emoji 宽度出问题；不要用字符数去做列对齐。

### 6.5 §13 风险表漏了什么？最坏情况下的用户体验与合规边界

漏了 3 类：

1. **最坏情况没有兜底**（M2）：R1 说"致命 + 给报错"，但那时工具**什么都不产出**。→ 加 `--from-json` / `--demo`，保证"接口挂了也能出完整报告"。
2. **合规/平台边界**（M11-R7/R8）：抓取公开评论用于个人研究风险低，但工具是**公开分发 + 支持批量 BV + 输出带真人昵称的 CSV**，这三件事叠起来在"批量采集""挂人名单"方向上有明确的滥用面。→ `--anon`、README 红线、不提供批量循环参数。
3. **输出被断章取义**：§11.3 只要求**摘要**带免责声明，而 **CSV 会被单独转发**。→ 免责声明也写进 CSV。

另：R2 的 `-352` 我在旧端点上**真的撞到了**，建议把 R2 的概率从"中"上调，并把 `-352` 的中文提示写进规格（M4）。

### 6.6 §14 的验收标准可度量、可复现吗？

- **M1 部分可度量**（完整度 ≥98%），但**没给公式**，两个人会算出两个数 → 补公式 + 强制 `is_end === true`（M13）。
- **M2 完全不可度量**："人工抽查 30 条命中，准确率 ≥80%"没有定义"准确率"、没有抽样规则、没有可跑的命令、没有落盘的数据集 → 按 M14 改成"随机 200 条 + 人工标注 + `eval.js` + precision ≥ 0.8"。**注意 30 条样本太小**：80% 的置信区间宽到 ±14pt，等于没验收。
- **M3 需要补充"怎么模拟失败"**："无网络/无 AI 时不崩"要写清步骤：断网跑一次 + 把 baseUrl 指向一个不存在的端口跑一次，并把两种期望输出写进 §14。

### 6.7 从"发 B 站视频"反推：观众最可能在哪一步放弃？

按放弃概率排序：

1. **第 0 步：没装 Node / 不知道 Node 是什么。** §12 只说 README"面向不会编程的人写三步走"，但整份 SPEC **没有描述陌生人第一次运行的三分钟长什么样**。建议加一节"§3.1 陌生人首次运行路径"，把 README 骨架定死：第一步必须是**装 Node 的指引 + `node -v` 自检**，而不是 `git clone`。
2. **复制链接这一下（最可能的当场翻车）：App 分享出来的是 `【标题】 https://b23.tv/xxx`**，解析器大概率不认（M12）。**录视频前请务必用真实分享文本试一次。**
3. **Windows 终端里的中文乱码 / 编码 / `>` 重定向**（M6 + 代码页）。
4. **命令太长记不住**：首屏只给**一条**命令 `node huashu.js "<粘贴链接>"`，其余选项放到后面的表。
5. **跑完有一堆 CSV 但不知道看什么**：所以 §11.1 的终端摘要就是**全部体验**，它必须第一屏就给出结论，并补一句"建议下一步：把 CSV 按 `max_score` 排序看前 20 条"。
6. **跑出来只有 3 条**（风控降级，B2）→ 观众直接判定"这工具是假的"。

**§3 的使用场景（S1–S6）覆盖了"会用的人"，但没有覆盖"第一次运行的人"。** 这 6 步建议直接写成 README 骨架，并给每一步规定**失败提示文案**——这比多写 200 行代码更能决定这期视频的口碑。
