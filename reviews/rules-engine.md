## 0. 60 秒结论（大白话版）

三层架构（词表召回 / 句式打分 / 语境排除）方向是对的，业界做规则型分类器基本就是这个骨架。**但当前规格里有两个会当场翻车的结构性错误：**

1. **默认配置会亲手杀掉规格自己写的正例。** 扣帽型的原型是「女仆装不就是媚宅、软色情？」，而 `不就是` 恰好被写进了 §6 的 L3 排除词表 `negationBefore`。这句话会被判定为"否定/元话语语境"，整类分数 ×0.3 → 1.0 变 0.3 → 不报。**演示 T5/T6 时会出现"一条都出不来"。**

2. **L3 在真实样本上一条都没拦住。** 主人给的 S-1「牛逼,评论区各种理中客,各打五十大板了」和 S-2「请勿被评论区话术欺骗……理中客各打五十大板」，现在之所以没误报，靠的是"命中 2 个词 × 0.25 = 0.50 < 0.60"这个**纯数值巧合**，跟"它是在骂和稀泥的人"这个语境判断毫无关系。把 `lexiconWeight` 从 0.25 改成 0.30，这两条会**同时变成误报**。也就是说：L3 现在既没救回真话术，也没拦住假话术，它是装饰品。

配套的两个次要但会被观众当场抓住的问题：

3. **§11.1 的示意输出自相矛盾**：逐类条数 118+96+71+54+38+35 = 412，正好等于"命中 412 条"。但 §7.2 明写"一条评论可同时命中多类"。这两个数不可能同时成立。（如果这张图出现在视频里，评论区第一条质疑就是它。）
4. **M2 验收"人工抽查 30 条命中，准确率 ≥ 80%"当前不可判定**：它只抽查"命中"（只测精度，完全没测漏检），而且 30 条样本、24/30 命中的 95% 置信区间是 **63%–90%**——过没过说不清楚。

**判断基线（回答任务问题 1）**：三层结构在原理上**能**达到"抽查命中准确率 80%"，但它成立的前提是"每条 pattern 单独命中就已过阈值"。一旦为了提召回加入 0.3–0.5 权重的弱句式（M2 的"误报能被压住"这句话迟早会逼你加），当前公式会立刻让"弱句式 + 2 个词表词"顶过阈值，精度掉到 50–65% 区间。**能不能过 80%，取决于规则编写纪律，而不是架构本身——这恰恰说明公式必须改。**

## 2. 先说"已验证无误"的部分（避免主人以为我漏看了）

这些地方我认真过了，**设计是对的**，不用改：

- **§1.2「不做立场判定」**：正确，而且是检测质量的前提。一旦引入立场轴，就必须先判立场再判话术，误差会串联放大。**但**要补一句后果声明（见 §6 的 F-15）：摘要里的类别计数**不能**被解读为阵营分布。
- **§7.3「没有证据的命中一律不输出」**：这是整份规格里最有价值的一条。它是唯一能在误报发生时救回公信力的设计，必须硬化成"每条候选在内存里就必须携带证据对象，否则不允许进入 Hit 列表"。
- **§6.1「正则编译失败该条跳过并警告，不整体崩溃」**：对的容错粒度。
- **§12「Detector 是纯函数 + Fetcher 接受注入」**：对的。这条让下面的"原型回归夹具"成为可能——这是本审查强烈建议的东西，正因为 Detector 是纯函数它才 5 行就能跑起来。
- **§7.2 的 `(1 − penalty)` = 1 − 0.7 = 0.3 与 §6 默认 `penalty: 0.7`**：数值自洽，无反证。
- **§11.2 的 evidence 格式（T1:pattern(...)@12-24）**：方向正确，可追溯性够用（细节问题见 F-18）。
- **§7.2「一条评论可同时命中多类」**：这个决定是对的（多标签比硬分类诚实），错的只是 §11.1 没按它来展示（F-15）。
- **"引号包裹 + 前置否定词"作为 L3 的**方向**：这就是业界说的 attribution / quotation gate，思路没问题；问题全在粒度和覆盖率（F-01、F-02）。

## 3. BLOCKER 级问题

### F-01【BLOCKER｜写错】`不就是` 在 L3 排除词表里，会系统性压掉扣帽型的原型句式

**问题是什么**

§6 的默认配置：

```json
"contextGuards": {
  "negationBefore": ["别被", "谨记", "常识", "所谓", "不就是", "经典", "警惕", "识别"],
  "negationWindow": 12,
  "penalty": 0.7
}
```

而扣帽型的原型（任务清单第 5 条、§6.1 归入 common 包）是：

> 女仆装**不就是**媚宅、软色情？

按 §7.1/§7.2：`媚宅`、`软色情` 两个词表命中 → 0.25 × 2 = 0.5；再加一条 T5 的句式和 0.8 → raw = 1.0 → min(1, ·) = 1.0；然后 L3 命中（`不就是` 在 `媚宅` 前 3 个字，远在 12 字窗口内）→ 1.0 × 0.3 = **0.3 < 0.6 → 不报**。

**为什么是问题**

`不就是……吗？` 在中文里是**标准的扣帽/定性句式**（"X 不就是 Y 吗"= 把 X 直接判定为 Y，且带反问的压迫感），不是否定标记，不是引用标记。规格把 L3 的"排除词"和"反讽/元话语词"混在同一个列表里，还把这类词的语义搞反了，结果是**默认配置主动压制了它本该识别的目标类别**。演示视频里讲 T5/T6 的时候一条都出不来，这是最典型的当场翻车。

顺带：这个列表的语义混杂本身也是问题——`别被/警惕`是**否定型**（说话人在提醒别人别信），`所谓/号称`是**元话语型**（说话人在引述别人的说法），`不就是/经典`是**反讽型**（说话人在嘲讽）。三类的行为完全不能用一个 penalty 处理。

**具体怎么改**

1. 从 `negationBefore` 里**删掉 `不就是`**，把它变成扣帽型的**正例句式**：

```json
{ "re": "不(就)?是.{0,8}(媚宅|软色情|rsq|擦边|性化|物化|媚男|媚女)", "score": 0.8 }
```

2. 把 `contextGuards` 拆成三个语义清晰的组，各自带自己的权重：

```json
"contextGuards": {
  "quote":      { "penalty": 0.9 },
  "meta":       { "words": ["所谓", "号称", "自称", "打着", "冠以", "美其名曰"], "penalty": 0.7 },
  "negation":   { "words": ["别被", "不要被", "勿被", "请勿", "谨防", "当心", "小心", "提防", "警惕", "识破", "看穿", "拆穿", "别信", "别上当"], "penalty": 0.8 },
  "sarcasm":    { "words": ["对对对", "行行行", "是是是", "呵呵", "笑死", "典中典", "难绷", "绷不住"], "penalty": 0.5 },
  "window": 12
}
```

注意 `penalty` 的语义在这里被我改成了「乘以 (1 − penalty)」，quote 的 0.9 意味着降到 0.1（引用基本等于作废），而 sarcasm 的 0.5 意味着降到 0.5（反讽是弱信号，因为反讽的人**也可能同时是话术使用者**）。同时 `经典` 从列表里拿掉：真实样本 S-1 里「**经典**逆风装无辜」是说话人在**嘲讽对面**，把它当引用标记会把真话术也一起压掉。

3. **在 §7.1 加一句硬约束**：任何新增的 guard 词/句式，必须先通过"9 条原型正例不被压制"的回归测试（见 F-12 的夹具），否则不允许进默认规则包。

**严重度理由**：默认配置直接压制默认规则包里目标类型的原型样例，演示必翻车。

### F-02【BLOCKER｜写错】L3 的粒度与覆盖率都不成立——它在真实样本上命中数为 0

**问题是什么**

现在 L3 的定义是「引号包裹 **或** 命中词前 N 字内有否定/元话语标记」，命中后**整条评论该类型的总分 ×0.3**。它同时有三个毛病：

**(a) 粒度错了：一次引用，全类连坐。** 一条长评论在第 1 段引用了对方的话术，在第 3 段自己使用话术，全类的分都被 ×0.3。正确做法是**逐次命中判定**：被引用的那次命中不该计分，没被引用的那次照常计分。

**(b) 窗口是单向的，只往前看。** 真实中文里标记经常在**被命中的片段之后**：「还好意思说 q 版的 rsq？」「都别吵了行不行？」「这就叫信息茧房？」——反问尾缀全在后面。

**(c) 覆盖不到最常见的引用方式：无引号的转述。** 主人的 S-2 就是铁证：

> 给大肥鱼爱好者们提个醒，**请勿被**评论区**话术**欺骗……（中略）……**理中客各打五十大板**

我按 §7 的公式逐字算过（见 §5 回放表）：这句里 `理中客` + `各打五十大板` 两个词命中 T1 词表 = 0.25 × 2 = **0.50**；T1 的两条 pattern 都因为 8 字窗口差一点没命中；`exclude` 的正则是 `(别|不要)被.{0,6}(话术|带节奏)`，**「请勿被」不在其中**，所以 exclude 也没触发；`negationBefore` 里**没有 `请勿`**，所以 L3 也没触发。结论：这句话没被误报，**靠的是"命中词数刚好是 2"这个巧合**，跟语境判断一点关系都没有。

补一个可复现的反证：**把 `lexiconWeight` 从 0.25 改成 0.30**（一个非常自然的"我想多召回一点"的念头），S-1 和 S-2 的分数同时变成 0.60 ≥ 0.60 → **两条真实误报同时出现**。同样地，把 `lexiconCap` 从 2 提到 3，0.25 × 3 = 0.75，那么任何同时出现「看戏 + 都有道理 + 各退一步」的普通客套评论都会被判成和稀泥。

**为什么是问题**

§7.1 把 L3 的职责写成"区分使用者 vs 识破者"，这是整份规格里最难也最关键的一环。但按现在的定义，它在主人提供的两条**专门用来测它**的真实样本上命中数为 0。也就是说，工具宣传的"能识破引用"这个能力，目前是不存在的。

**具体怎么改**（仍然只用正则/字符串，不上模型）

**改 1：把 guard 从"整条降权"改成"逐次命中降权"。** 算法改成：

```
对每个命中 m（一条 pattern 匹配，或一次词表出现）：
  kind = guardKind(m.span, text)   // none | quote | meta | negation | sarcasm
  若 kind 非 none:  eff(m) = m.score × (1 − penalty[kind])
  否则:             eff(m) = m.score

patternScore = min(Σ eff(pattern), patternCap)         // 新增 patternCap，默认 1.0
lexiconScore = lexiconWeight × min(Σ eff(lexicon 出现次数), lexiconCap)
              // 被 guard 掉的词表出现次数按 eff 折算，不再简单计数
raw   = patternScore + lexiconScore
score = min(1, raw)
```

这样"引用一次"只影响那一次命中，不再连坐全类；同时 `guardNote` 天然变成 `"quote×1, negation×1"` 这种可核对的字符串。

**改 2：扩充 guard 集合，把下面 6 种真实中文句式覆盖进去**（每条都是可直接写的正则/字符串规则，我在 §4 给了完整清单）。

**改 3：把 L3 的判定结果写进 CSV 的证据链**，字段格式与 §11.2 的 evidence 保持一致，例如
`T1:pattern(都别吵了)@0-5!guard:quote@0-24`。

## 4. L3 会漏掉的 6 种真实中文句式 + 可实现的补法

这是任务问题 3 的正面回答。全部只用正则/字符串，零模型。

### (1) 无引号的转述 / 复述 —— 最高频，也是主人真实样本踩到的那个

**例子**：「请勿被评论区话术欺骗……理中客各打五十大板」「他们说都别吵了」「楼上说得对：两边都有问题」

**为什么漏**：现在只有"引号包裹"才认引用，但中文网络评论里大量引用是不加引号的，靠"报告动词 + 冒号"来标记。

**怎么补**：加一组报告动词 + 邻近判定（不是引号判定）：

```json
"reportVerbs": ["说", "讲", "道", "云", "曰", "认为", "觉得", "表示", "声称", "号称", "自称", "写", "评论", "回复", "提到", "原话", "引用", "转发", "贴"],
"reportWindow": 15
```

规则：若命中片段的起点之前 `reportWindow` 字内出现报告动词，且中间没有断句符（。！？；），判为 `meta`。另外把 §6 的 `exclude` 正则从 `(别|不要)被.{0,6}(话术|带节奏)` 扩到
`(别|不要|勿|请勿|谨防|当心|小心|提防|警惕|识破|看穿|拆穿)[被上].{0,8}(话术|带节奏|节奏|骗|忽悠|当)`
——主人在 S-2 里写的「请勿被……话术欺骗」正是被现有 exclude 漏掉的那一种。

### (2) 后置反问 / 反问定性

**例子**：「还好意思说 q 版的 rsq？」「都别吵了行不行？」「这就叫信息茧房？」「你们也配讲理中客？」

**为什么漏**：现在只有"命中词前 12 字"这一个方向，而反问的标记词（吗/呢/吧/行不行/也配/算不算）全在片段之后。

**怎么补**：加**双向**窗口和后缀表：

```json
"rhetorical": {
  "prefix": ["难道", "难道说", "岂", "凭什么", "怎么就", "谁", "这也叫", "也配", "算不算"],
  "suffix": ["吗", "呢", "吧", "行不行", "好不好", "是不是", "能不能", "也配"],
  "suffixWindow": 8,
  "penalty": 0.6
}
```

注意：反问是**弱**信号（"都别吵了行不行"本身就是在和稀泥，只是语气更冲），所以 penalty 只能给 0.6 左右——给 0.9 会把大量真话术也一起压掉。

### (3) 后置反讽 / 阴阳怪气

**例子**：「对对对，两边都有问题，您说得都对」「确实，毕竟理中客最客观了」「笑死，还各打五十大板呢」「典」

**为什么漏**：现有 `negationBefore` 里虽然塞了 `经典`，但方向是前向、且没有重复字/固定讽喻词的检测。

**怎么补**：

```json
"sarcasm": {
  "phrases": ["对对对", "行行行", "是是是", "好好好", "呵呵", "笑死", "笑不活了", "典", "典中典", "乐", "难绷", "绷不住", "毕竟", "您说得都对", "受教了"],
  "repeatChar": { "minRepeat": 3, "maxSpan": 6 },
  "penalty": 0.5
}
```

`repeatChar` 的判定不加正则也能做：扫描连续 6 字内是否有同一个单字出现 3 次及以上，命中即判反讽。**必须拿 9 条原型跑回归**——原型 4「散了吧，一个AI形象而已」里的 `而已` 是消解型的**使用标记**，绝不能进 sarcasm 表。

### (4) 假设 / 借用对方框架（归谬式引用）

**例子**：「按你的**逻辑**，两边都有问题？」「照这么说，你们都别吵了」「如果按理中客的**说法**」「顺着这套**思路**」

**为什么漏**：这是"引用"的一种，但既没有引号也没有报告动词，靠的是框架前缀。

**怎么补**：

```json
"framePrefix": ["按你的", "按你们", "照你", "顺着", "依你", "如果按", "要是按", "按这套", "照这套", "依这套"],
"frameNoun": ["逻辑", "说法", "思路", "标准", "理论", "观点", "套路", "话术"],
"frameWindow": 12,
"penalty": 0.7
```

判定：`framePrefix` 与 `frameNoun` 都在命中片段前 `frameWindow` 字内出现 → 判 `meta`。

### (5) 平台格式引用（转发 / 回复 / 楼层 / @）

**例子**：「回复 @大肥鱼爱好者 : 你说的都对」「//@某某: 都别吵了」「>>123楼」「引用自……」

**为什么漏**：`quoteChars` 里只有成对符号，没有任何平台格式前缀。

**怎么补**：在匹配前**剥掉**这些前缀并记入 `prefixStripped`（剥掉比判定更稳，因为这类前缀本身没有任何检测价值）：

```json
"quotePrefix": ["回复 ?@[^:：]{1,24}[:：]", "//@", ">>[ ]*[0-9]+楼", "引用自", "转载自", "原话[:：]"]
```

另外 §6.1 的 `quoteChars` 里，`《》` 建议**保留**（书名号引用是可靠的），但要**去掉任何可能被当作表情括号的符号**——B 站正文里的方括号 token（`[大笑]`、`[FGO_好耶]`，1–12 字）如果被当成引号，会让整段文本误判为"被引号包裹"。要么在归一化阶段把方括号 token 替换成一个占位符，要么就干脆不把方括号放进 `quoteChars`。

### (6) 引号配对失败 / 嵌套 / 未闭合

**例子**：「他说"两边都有问题"然后又说"各打五十大板"」（嵌套同型引号）、「我觉得"（引号打了一半就发出去了）」

**为什么漏**：规格里 `quoteChars` 是一个字符串数组 `["「」", "..", ".."]`，**没有说明是"成对匹配判定"还是"出现过就算"**。如果实现成"文本里出现过任意引号字符就算引用"，那么任何带一个 `"` 的评论全类降权；如果实现成"整段文本首尾都被包住"，那么 S-2 这种"中间夹着引用"的完全漏掉。

**怎么补**：在 §7.1 明确写成**成对扫描 + 栈**：

```
扫描全文，遇到开符号压栈、遇到同型闭符号弹栈；
每个命中片段的区间若完全落在某对配对区间内 → 判 quote；
未闭合的开符号视为"引用到文本结尾"；
不同类型引号嵌套时以最内层为准。
```

这是十几行代码的事，但必须写进规格，否则不同人实现的 L3 结果完全不同。

## 6. 对任务 7 个问题的正面回答

### Q1：§7 的三层结构在原理上能不能达到"抽查 30 条准确率 ≥80%"？

**能，但当前规格下这个"能"没有意义，因为它不可判定，且按类型会严重分化。**

**判断依据：**

1. **先说好的**：在**默认权重**下，公式实际等价于"任意一条 pattern 命中即过阈值"。因为 `lexiconWeight × lexiconCap = 0.25 × 2 = 0.5 < threshold 0.6` —— 纯词表**永远无法单独触发**。所以默认配置下的精度 ≈ 最强/最泛化那条 pattern 的精度。T1 的 `都别(吵|争|骂|打)了`（0.9）和 `(两边|双方|大家).{0,8}(都|各).{0,8}(有问题|有错|不对|五十大板)`（0.8）这类骨架，precision 落在 70–85% 是合理预期。

2. **但这个性质是隐式的、脆弱的**：规格从头到尾没写过"lexiconWeight × lexiconCap 必须小于 threshold"，也没在加载时校验。任何一个把它改成 0.5 或把 cap 改成 3 的人（包括主人自己调参时），都会瞬间打开纯词表误报的闸门。**安全边界靠一个没人写下来的不等式维持，这是不能接受的。**

3. **一旦为了提召回加弱 pattern，精度立刻崩**。M2 写着"误报能被 exclude 或调阈值压住"——这句话的实际含义是"你会想去补规则"。但加一条 0.4 权重的弱 pattern 后，"弱 pattern(0.4) + 词表 2 词(0.5) = 0.9" 远过阈值；甚至"弱 pattern(0.4) + 词表 1 词(0.25) = 0.65" 也过。此时类型的精度上限由**最弱的那条 pattern** 决定。这是 F-03 的核心。

4. **按类型看会严重分化**（这是主人必须提前知道的）：
   - T1 和稀泥 / T2 假中立 / T8 胜利后劝和：词汇与句式**只被使用者用**，precision 预期 80–90%；
   - T5/T6 扣帽型：词（媚宅、软色情、贬低女性）**双方都在用**——被扣帽的一方在反驳时也会把这些词写出来。**如果不修 L3，precision 预期只有 50–65%**；
   - T7 信息茧房型：`信息茧房` 现在是一个"骂人的词"，真实样本里 3 次出现全是在嘲讽对面（S-2、样本 13），而不是在用茧房逻辑压人；
   - T9 反饭圈型：**最容易翻车的类型**。「别搞饭圈那套」在争论双方口里出现频率接近五五开，且多数是**真诚的方法论主张**而非话术。precision 预期 45–60%。**建议 v1 把 T9 标记为 `enabled: false` 的实验性类型**，或强制它必须有"饭圈"+"官方"双证据才计分。

5. **验收标准本身不可判定（F-08）**：
   - 只抽"命中" = 只测 precision，**召回率零测量**。工具漏掉的话术永远不出现在样本里，所以"识别不准"这个风险有整整一半没被验收覆盖。
   - n=30、24/30 命中的 Wilson 95% 置信区间是 **[63%, 90%]**。也就是说结果可能是"刚好过"，也可能是"其实只有 63%"。用它来判"≥80%"是不合格的测量。
   - 按类型抽样的需求：30 条里 T1/T2 占一半（118+96=214，占 412 的一半），于是**整体准确率会被容易的类别拉高**，难的类别（T9/T7）的失败在 30 条里根本看不出来（30 条 / 6 类 ≈ 每类 5 条，5 条的置信区间毫无用处）。

**具体怎么改（写进 §14 M2）：**

> M2 验收改为三项，全部可复现：
> 1. **逐类精度**：从每类命中里随机抽 ≥15 条（用 `--sample 15 --seed 42`，种子固定以便视频里复现），人工判定，报告每类精度与其 95% 置信区间。**任一类低于 60% 则必须默认关闭该类型，或补规则后重测。**
> 2. **召回抽检**：随机抽 30 条**未命中**的评论，人工看是否漏了话术；漏检率作为已知局限写进 README（"本工具是筛子不是网"）。
> 3. **夹具回归**：§7 附带的原型夹具（见 Q3 末）全部通过。

### Q2：§7.2 打分公式的结构性缺陷

公式：

```
raw = Σ(pattern.score) + lexiconWeight × min(命中词数, lexiconCap)
score = min(1, raw)
L3 命中 → score × (1 − penalty)
命中 = score ≥ threshold
```

**缺陷 1：没有闸门，词表是加了引号的触发器。**
"弱 pattern 0.4 + 2 个词表词 0.5 = 0.9" 与 "一条强 pattern 0.9" 得到同样的结论。但前者只是"关键词撞上了"，后者才是"句式成立"。**语法的证据和词汇的证据共用一个加法池，是这类系统最经典的设计错误。**
→ 改成两段式：

```
patternScore ≥ patternGate (默认 0.5)  且  score ≥ threshold
```

这样"必须有至少一条句式成立"成为硬约束，与你把 lexiconWeight 调成多少无关。

**缺陷 2：`min(词数, cap)` 用命中数量冒充证据强度。**
"字数多"不等于"证据强"。T1 词表里 `各打五十大板`（强、罕见、几乎只在和稀泥语境出现）和 `看戏`（弱、极常见、"吃瓜看戏"到处都有）被算成同样 0.25 分。`看戏` 应该直接删掉。
→ 词表项支持对象形式，带独立权重：

```json
"lexicon": [
  { "w": "各打五十大板", "weight": 1.0 },
  { "w": "理中客",       "weight": 0.4, "note": "多数情况下是骂人的那一侧，见 F-04" },
  { "w": "看戏",         "weight": 0.0, "note": "保留仅用于文档，不参与计分" }
]
```

（字符串形式继续作为 `weight = 1.0` 的简写，后向兼容。）

**缺陷 3：`min(命中词数, cap)` 的截断位置可疑。**
`min(...,2)` 意味着第 3 个词开始完全没有贡献。在"短评论"上没问题，但一条 300 字的长评论同时出现 5 个 T1 词和一条 300 字评论出现 2 个词，**得分一样**。真实数据里长评论正是误报的重灾区（长评论撞上任何规则的概率更高）。
→ 建议：词表分改为**边际递减**而不是硬截断，例如 `1 + 0.5 + 0.25 + ...`，或者干脆保持硬截断但把 F-03 的 patternGate 作为主判据（词表只做排序用）。
这个可以二选一，不必都做。

**缺陷 4：阈值 0.6 凭什么？**
**没有任何依据，规格里也没给校准方法。** 更要命的是：在 §6 给的样例里，pattern 分只有 0.8 和 0.9 两档，此时"score ≥ 0.6"和"命中任意 pattern"**完全等价**——**阈值 0.6 在这个规则集里是个吉祥物，它一次都没有真正参与过判定**。
→ 在 §7.2 补一段"分档约定"，让阈值真正有意义：

> - `score 1.0`：完整复现了该类话术的句式骨架（例如 `都别吵了`）；
> - `score 0.7`：结构成立但有缺件（例如只出现了"两边…都有问题"的一半）；
> - `score 0.4`：共现型弱信号，**单独命中不允许过阈值**（由 patternGate 保证）；
> - `threshold` 默认 0.6，含义是"必须有一条 ≥0.5 的句式命中，且总分过线"。
>
> 阈值的选取方法：在 60 条人工标注样本上跑，取 precision ≈ 0.85 对应的最小阈值。**不要拍脑袋定 0.6。**

**缺陷 5：`min(1, raw)` 饱和破坏了排序能力。**
命中 5 条 pattern 和命中 1 条 pattern 都显示 1.00，没法按置信度排序，也没法做"最可疑的 10 条"这种对视频极有价值的展示。
→ 保留 `score = min(1, raw)` 作为判定值，但**另存 `rawScore`**（不饱和）到 Hit 与 CSV，用于排序和调试输出。

**缺陷 6：重复命中未定义（F-07）。** 见 Q4。

### Q3：L3 的覆盖能力

已在 **§4** 完整回答：给出 **6 种会漏掉的中文句式**（无引号转述 / 后置反问 / 后置反讽 / 框架借用 / 平台格式引用 / 引号配对失败），每种都配了可实现的判定方式和 JSON 片段。这里只补三条**跨切面**的结论：

1. **"一对一的替换是解决不了 L3 的"，必须改结构**：现在 L3 是"给整条评论乘一个系数"，即使你把词表扩到 100 个词，粒度错误依然存在（一次引用全类连坐）。**先改粒度（F-02 改 1），再扩词表**。
2. **guard 之间会互相打架**：`不就是`（本应是正例）和 `经典`（弱反讽）现在同一张表、同一个权重；`请勿被…话术`（强否定）和 `对对对`（弱反讽）也不该同权重。分成 `quote / meta / negation / sarcasm / rhetorical` 五组、各自 penalty，是能同时提高精度和可解释性的最小改动。
3. **必须建立"原型夹具"**，否则每加一个 guard 都可能打坏另一个类型——而且**这次已经发生过一次了**（F-01）。夹具就是一张表：

```json
[
  { "text": "都别吵了，两边都有问题",            "expect": { "T1": true },  "note": "原型1 正例" },
  { "text": "女仆装不就是媚宅、软色情？",         "expect": { "T5": true },  "note": "原型5 正例（当前被不就是压掉）" },
  { "text": "散了吧，一个AI形象而已",             "expect": { "T4": true },  "note": "原型4 正例（别被 sarcasm 误伤）" },
  { "text": "别搞饭圈那套，官方都没定",           "expect": { "T9": true },  "note": "原型9 正例" },
  { "text": "牛逼,评论区各种理中客,各打五十大板了", "expect": { "T1": false }, "note": "真实样本 S-1 引用/嘲讽" },
  { "text": "请勿被评论区话术欺骗……理中客各打五十大板", "expect": { "T1": false }, "note": "真实样本 S-2 转述" },
  { "text": "对对对，两边都有问题，您说得都对",     "expect": { "T1": false }, "note": "反讽" },
  { "text": "按你的逻辑，两边都有问题？",           "expect": { "T1": false }, "note": "归谬引用" },
  { "text": "还好意思说 q 版的 rsq？",             "expect": { "T5": false }, "note": "反问嘲弄" }
]
```

每条给 `expect` 与 `note`，跑 `node huashu.js --selftest` 输出 pass/fail。**这是整份规格里性价比最高的一项投入**，理由有三：(a) 它防止"修 A 打坏 B"；(b) 它是视频里最有说服力的一段——"我准备了 20 条刁钻样本，当场跑给你看"；(c) 它把 M2 那句含糊的"准确率 80%"变成可执行的断言。而且因为 §12 已经规定 Detector 是纯函数，这个自测**不需要网络、不需要抓取**，几十毫秒跑完。

### Q4：§6 的规则 JSON schema：够不够当"社区扩展口子"？

**结论：不够。它够表达"一份写死的默认规则"，但不够表达"一份别人能改、能合并、能迁移、不会把工具搞崩的规则"。**

**缺的字段（按重要性排序）：**

| 缺什么 | 为什么必须补 | 建议的字段 |
|---|---|---|
| **pack（包归属）** | 现在包归属由"文件"承载，导致"通用骨架 + 事件词表"没法表达（见 Q6） | `types[].pack` + `lexicon[].pack` |
| **enabled / status** | T9、T7 这类低精度类型必须能"随包发布但默认关闭" | `types[].enabled`（默认 true）、`types[].status: "stable" \| "experimental"` |
| **family（归并轴）** | 9 个类别目前没有归并关系，报告只能给 9 个孤立数字；T1/T2/T8 同属"劝和"，T5/T6/T7 同属"定性/扣帽" | `types[].family: "劝和" \| "扣帽" \| "消解" \| "元讨论"` |
| **词条权重** | 见 Q2 缺陷 2；等权词表是和稀泥/扣帽型误报的主要来源 | `lexicon[]` 支持 `{w, weight, pack, note}` |
| **patternGate** | 见 Q2 缺陷 1；这是把"必须有句式证据"变成硬约束的唯一手段 | 全局 `patternGate`（默认 0.5）+ `types[].patternGate` 覆盖 |
| **patternCap** | 防止同类型多条 pattern 叠加堆分 | `types[].patternCap`（默认 1.0） |
| **正则 flags** | 见 F-05，不规定就会出实现分歧和 lastIndex 陷阱 | 全局 `flags: "iu"`，**明确禁止 g / y** |
| **规则文件指纹** | CSV 里的结论必须能回答"这是哪份规则跑出来的" | 报告里回显 `rulesName + version + sha256(规则文件)` |
| **正则性能约束** | 见 Q5 | `maxPatternLength`、加载期 lint 开关 |
| **AI 提示用元数据** | `examples` / `note` 现在语义不明 | 明确写：`examples` / `note` **不参与匹配**，仅供 §8 的 AI 提示和文档使用 |

**关于"类型之间的互斥/包含关系"**：我**不建议**在 v1 引入 `conflicts` / `implies` 这类关系图。理由：它会立刻把规则系统变成"需要一个推理机"的东西，属于过度设计。**用 `family` 一个字段就能覆盖 80% 的需求**（报告里能归并展示），而 T1/T2 的真假区别（"我是不是自称路人"）用一条 pattern 就能表达，不需要互斥声明。

**关于规则版本迁移**：`version: 1` 现在只做了"≠1 就报错退出"。这个够用，但要补一句：**规则文件里出现 `engineMin` 且当前引擎版本低于它时，报错退出并提示升级工具**，否则社区规则用到新字段（比如 `patternGate`）时，老版本工具的行为是"未知字段忽略" → **静默按错误的方式运行**，这比报错危险得多。

### Q5：性能与安全 —— `(a+)+$` 会怎样？是不是必须补的坑？

**会怎样**：这条正则不会编译失败（所以 §6.1 的"编译失败跳过"拦不住它）。它会在匹配一条含大量 `a` 的字符串时发生**灾难性回溯**：回溯次数随长度指数增长。对一条 60 个 `a` 的输入，回溯次数约 2^60；对一条 20 个 `a` 的长度就已经到百万级。

在这份规格里，后果是：**单条评论就能让进程卡死**（不是变慢，是不返回），而 Detector 是同步纯函数、跑在主线程上，所以 `--max-comments`、超时、Ctrl+C 全部无效——**整个工具表现为"卡住不动"，用户只能杀进程**。B 站评论区恰好存在大量重复字符（表情、谐音刷屏、"红红火火恍恍惚惚"），触发概率不低。

**严重度判定：MAJOR（不是 BLOCKER）。** 诚实说明理由：默认规则包里不会出现这种正则（主人自己写的规则是可控的），所以**拍视频、跑默认规则不会当场翻车**。但只要这份工具按 §1.1 的"抛砖引玉、社区接手"定位发出去，**第一个社区规则文件里出现 `(.+)+ ` 只是时间问题**——而且它发生在别人机器上，你收不到报错。所以：**默认规则下 MAJOR，一旦承诺支持第三方规则就是 BLOCKER。**

**必须补的四件事：**

1. **强制剥离 `g` / `y` flag（F-05，这条和 ReDoS 同等重要）。**
   如果规则里写了 `/都别(吵|争)了/g`，实现里用 `re.test(text)` 逐条评论调用，**同一个 RegExp 对象的 `lastIndex` 会在两次调用之间残留**，导致它对同一条文本交替返回 true / false。表现出来就是"同一份规则，跑两次结果不一样"——这是最难排查的一类 bug，而且它会污染 M2 的验收数据本身。
   → 在 RuleSet 加载时：`flags = "iu"`（强制，忽略用户写的 g/y），理由写进 §6。

2. **加载期静态 lint，拒绝明显的回溯炸弹。** 在 `load()` 里对每条 `re` 做字符串级检查，命中就**跳过该条并警告**（沿用 §6.1 已有的"该条跳过、不整体崩溃"策略）：

```
禁止模式（字符串级检测，无需正则引擎）：
  1) 量词直接套在量词外面： "+)+"  "*)+"  "+)*"  "*)*"  "?)+" ...
  2) 分组内存在交替且分组被量化：形如 "(...|...)+"  "(.+)+"
  3) 单个字符类 + 无上界量词出现在组内： "(.+)+"  "([^x]*)*"
  4) 反向引用与量词组合
  5) 长度上限：单条 re 超过 200 字符 → 警告
```

   这不是万无一失（ReDoS 不可判定），但能挡住 95% 的实际写法，成本是 15 行代码。

3. **匹配前截断 + 归一化（F-11）。** 回溯的代价是输入长度的指数/超线性函数，把参与匹配的文本上限压到 500 字（超出部分截断并标 `msgTruncated: true`），能把"卡死"降级成"慢一点"。同时这条归一化管线本来就该有（零宽字符、全半角、字间插空格、emoji 占位）。
   **注意**：截断要在**归一化之后**计数，且要保留"原始字符 → 归一化字符"的索引映射，否则 §7.3 要求"原文片段与字符区间"就对不上了（F-18）。

4. **规则文件的安全定性写清楚。** 在 §6 补一句准确的说明：

> 规则文件中的正则**不构成代码执行**（`new RegExp` 不是 `eval`，不读取文件、不发网络请求），但**可以造成拒绝服务**（灾难性回溯会让进程无响应）。因此：只运行你信任来源的 rules.json；加载时执行静态 lint；单条 regex 长度上限 200 字符。

   这句必须准确，不要写成"任意代码执行"（这会吓跑用户，也不真实），也不要一字不提（社区规则会变成攻击面）。

**额外一条（顺带发现的原型污染）**：§6.1 说"未知字段忽略（不报错），缺失字段用默认值"。**这个语义天然诱导实现者写成 `Object.assign(defaults, userRules)` 或 `{ ...defaults, ...userRules }`。** 如果用户规则 JSON 里带了 `"__proto__"` 键，某些写法会造成原型污染。虽然这是本地小工具、影响面很小（MINOR），但成本是零：**明确写成"逐字段白名单读取，禁止对用户 JSON 做整体合并"。** 这是"规格没写但应该写"。

### Q6：9 类里哪些通用、哪些事件专属？§6.1 的分包合理吗？

**结论：9 类**没有一类**是"事件专属"的。事件专属的只是词表条目和示例。**

| 类别 | 骨架是否通用 | 事件专属成分 | 归属建议 |
|---|---|---|---|
| T1 和稀泥型 | 通用 | 无 | common |
| T2 假中立型 | 通用 | 无（"纯路人"是通用自称） | common |
| T3/T4 消解型 | 通用（"不如X"／"就这"／"一个X而已"／"散了吧"） | X = 奶鲸 / 奶龙 | **骨架进 common，填充词进 event** |
| T5 扣帽·软色情 | 通用（"不(就)是…吗"句式） | "女仆装"/"大肥鱼"是事件名词；**"媚宅/rsq/软色情"其实是通用词** | common（去掉事件名词） |
| T6 扣帽·性别 | 通用 | "把 AI 套女性形象"是本次议题 | common |
| T7 信息茧房型 | 通用 | "男版热度也高"是具体论据 | common |
| T8 胜利后劝和 | 通用（"你们已经赢了"） | "谁赢了"依赖事件 | common（骨架）+ event（战况词） |
| T9 反饭圈型 | 通用 | "官方都没定"是具体论据 | common |

**所以 §6.1 的划分点错了：它按"类型"分包，应该按"词条/句式条目"分包。** 现在的写法会造成两个具体后果：

1. **common 包里的"消解型"会是个空壳类型。** §6.1 把"消解"放进 common，但主人给的两个消解型原型（不如奶鲸 / 不如奶龙）全是事件词。按现在写法，common 包要么放一个没有词表的死类型，要么把"奶鲸/奶龙"塞进通用包（那就不是通用包了）。
   → 改成分包下沉到条目：

```json
{
  "id": "T3", "pack": "common", "name": "消解型",
  "lexicon": [
    { "w": "散了吧",       "pack": "common" },
    { "w": "就这",         "pack": "common" },
    { "w": "而已",         "pack": "common", "weight": 0.3 },
    { "w": "奶鲸",         "pack": "event-deepseek", "weight": 1.0 },
    { "w": "奶龙",         "pack": "event-deepseek", "weight": 1.0 }
  ]
}
```

   这样 `--pack common` 得到的是"通用的消解型识别"，`--pack all` 额外加上事件词，**同一类型不用写两遍**。

2. **"9 类"本身不是同一个切分维度，报告会有重复计数。** 细看这 9 类：
   - "劝和/消解冲突"族：T1 和稀泥、T2 假中立、T8 胜利后劝和、T4 消解
   - "给对方定性"族：T5 扣帽·软色情、T6 扣帽·性别、**T7 信息茧房**（"你只是信息茧房"本质就是一种扣帽，只是罪名不同）
   - "换赛道谈规矩"族：T9 反饭圈（把内容争议转成程序性质疑）

   也就是说 T7 和 T5/T6 是**包含关系**，一条评论可以合理地同时是"信息茧房型"和"扣帽型"。而 §7.2 又允许一条评论命中多类。结果就是摘要里的逐类百分比会重复计算同一条评论。
   → **v1 不要加轴**（那是过度设计），只加一个 `family` 字段用于归并展示。报告的呈现方式建议改成：

```
劝和类    249 条 (60.4%)   ├ T1 和稀泥 118
                           ├ T2 假中立  96
                           └ T8 劝和    35
扣帽类     92 条 (22.3%)   ├ T6 性别    54
                           └ T5 软色情  38
```

   这样观众看到的是"这场争论里，多少条是在消解冲突、多少条是在给对方定性"，**比 9 个孤立数字有信息量得多**，而且顺带解决了 F-15 的口径问题。

### Q7：如果只能保留 3 条改进建议

**第 1 条：把 L3 改成"逐次命中降权"，并把打分改成两段式闸门。**
（§7.1 + §7.2 一起改，约 30 行实现）

```
guardKind(span) → 只作用于"这一次命中"，不再乘以整条评论的类型总分
patternScore = min(Σ 有效 pattern 分, patternCap)
hit = (patternScore ≥ patternGate) 且 (score ≥ threshold)
```

理由：这一条同时修掉 F-02（引用连坐 + 覆盖不足）、F-03（弱句式堆分）、以及"纯词表误触发"的全部隐患。它是"识别准不准"这个问题的**唯一**杠杆点，其他所有调参都在这个公式下面。

**第 2 条：删掉 guard 里的 `不就是`，并建立 18 条原型回归夹具（9 条正例 + 9 条引用/反讽反例），做成 `--selftest`。**
（§6 改一个词 + §7 加一节，约 40 行实现）

理由：**这次审查里唯一一个"默认配置会杀掉默认正例"的 BLOCKER 就是这么来的**。夹具是防止它再次发生的唯一机制，同时它还是视频里最有说服力的素材（"我准备了刁钻样本，当场跑给你看"），成本几十毫秒、不需要网络。

**第 3 条：正则安全三件套 + 规则指纹。**
（§6 加一节，约 20 行实现）

- 强制 `flags = "iu"`，**剥掉 g / y**（否则同一份规则跑两次结果不同，会污染验收数据）；
- 加载期静态 lint 拒绝嵌套量词类回溯炸弹，命中就跳过该条并警告；
- 匹配前归一化 + 500 字截断（同时解决零宽字符、表情 token、emoji 窗口语义三件事）；
- 报告里回显 `rulesName + version + sha256(规则文件)`。

理由：§1.1 把工具定位成"给社区接手"，那么**规则文件就是外部输入**，外部输入必须有边界。而且这四项里有两项（flags、指纹）不修的话，**你连自己的验收数据都不可复现**。

**备选第 3 条（如果主人更在乎视频的可信度而不是工具健壮性）**：把 M2 的验收标准改成"逐类精度（每类抽 ≥15 条 + 置信区间）+ 30 条未命中抽样测漏检 + `--sample N --seed S` 可复现"。理由：现在的 80% 目标在统计上不可判定，你可能会在"以为过了"的状态下开拍。

## 7. 建议的 §7 最小改写草案（可直接抄）

如果主人只想要一份能直接替换的文本，下面是 §7.1–§7.3 的最小改写，不改架构、只改公式和 guard 定义：

```markdown
### 7.1 三层
| 层 | 作用 | 计分方式 |
|---|---|---|
| L1 词表 | 召回（提查全） | 每次命中按 词条权重 × (1 − guardPenalty) 计入，总数经 lexiconCap 截断后乘 lexiconWeight |
| L2 句式 | 准度（提查准） | 每条 pattern 命中一次计 score，经 guard 折算后求和，再由 patternCap 截断 |
| L3 语境 | 区分使用者 vs 识破者 | **逐次命中判定**：quote / meta / negation / sarcasm / rhetorical 五类，各自 penalty |

**L2 是唯一的触发通道**：patternScore < patternGate 时，无论词表命中多少词，该类一律不判命中。
（这条不变量取代了原先隐式的 "lexiconWeight × lexiconCap < threshold"，从此调权重不会炸。）

### 7.2 打分公式
    patternScore = min( Σ(有效 pattern 分), patternCap )          // patternCap 默认 1.0
    lexiconScore = lexiconWeight × min( Σ(有效词条权重), lexiconCap )
    raw          = patternScore + lexiconScore
    score        = min(1, raw)                                    // 用于判定
    rawScore     = raw                                            // 用于排序，不饱和（写进 CSV）

    命中判定: patternScore ≥ patternGate(默认 0.5)  且  score ≥ threshold(默认 0.6)

    有效 = 该次命中的原始分值 × (1 − guardPenalty)
    未被任何 guard 命中的命中项，折算系数为 1。

- pattern 一律以"每条规则在一条评论里至多计一次"为准（使用 test 语义，不做全局匹配）。
- 一条评论可同时命中多类。
- types[].exclude 命中 → 该类型归零，但**必须记录** exclude 的规则原文到 guardNote，供核查。

### 7.3 证据要求（不可省）
每条命中必须出示：
- 命中的规则来源：pattern:<正则原文> / lexicon:<词>（exclude 与 guard 同样要带原文）
- 命中的原文片段与字符区间（区间基于归一化后的匹配文本，同时给出未归一化的回查方式）
- 若被降权或归零，说明是哪个 guard / exclude 命中，以及命中位置
没有证据的命中一律不输出。
```

## 8. 附带回答：§15 的开放问题里与检测相关的两个

- **O4（Reporter 是否独立成模块）**：按"两个 adapter 原则"判，Reporter 有 **terminal / csv / json 三个**输出形态，不是浅模块，**应保留**。（这不是我的主审范围，仅供 §4 审查者参考。）
- **O5（`--limit-like` 只分析高赞）**：从检测角度**可以做，但必须改报告口径**。加了点赞门槛之后，分母从"全部主评论"变成"高赞主评论"，摘要里那句"命中 412 条 (22.9%)"的含义就变了，必须改写成"占高赞评论的 X%"。否则观众会拿它和全量数字直接对比，从而得出错误结论。另外高赞门槛会系统性筛掉新评论，而**新评论恰好是"反饭圈型/劝和型"出现最多的时段**，样本会有时间偏差——如果做这个功能，摘要里要标注抓取时的排序方式（§9.1 用的是 `mode=2` 时间序，与观众在页面上看到的"热度序"不同，见 F-24）。
